# 場景：議題池怎麼選

## 30 秒先看這段

雙重重大性的第一個工序是「議題池怎麼來」。過去你要翻 GRI Sector Standard、翻同業報告書、翻媒體、翻監管要求，把候選議題湊到 30+ 個再跟客戶刪。susr 幫你三方合併（產業包 + 框架標準 + 客戶上年議題），3 分鐘給你完整候選 list，並支援雙軸評分 + 議合事件結構化。

省下的時間讓你去做更有價值的：跟客戶 CSO 一對一聊「哪些議題在你們董事會層級真正有討論過」。

---

## 痛點

議題池建立階段的真實挑戰：

- **候選議題湊不齊**：你怕漏掉某個關鍵議題，被確信師或同業比下去
- **產業特化議題難找**：通用框架（GRI 通用準則）給你的是 universal topics，旅館業特有（顧客健康安全、文化襲產）要自己想
- **跨年連續性難維持**：上年的 28 個議題哪些今年仍重大？哪些可降階？哪些新冒出來？
- **議合資料散在 Email / Excel / 訪談錄音**：要把員工問卷 N=254 對到具體 topic_slug 很費工

---

## 過去怎麼做

典型 workflow（每個客戶大約 8-12 小時）：

1. 翻 GRI Sector Standard PDF 抄通用議題（2 小時）
2. 找 3-5 家同業最新報告書 PDF，抓他們列的核心議題（3-4 小時）
3. 翻監管要求（金管會公告 / SASB Standard）補議題（1 小時）
4. 跟客戶 CSO 開議題池會議，逐項討論去留（2-3 小時）
5. 把員工問卷 / 客戶問卷結果對到 topic 上（2 小時）
6. 整理成議題池 Excel + 利害關係人議合表

跑完一輪你大概已經疲勞。

## 用 susr 怎麼做

### Step 1：拉產業議題池（30 秒）

```
顧問：幫 acme-textile 拉紡織業議題池，框架 GRI，列前 40 個。

Claude：[呼叫 search_topics_universe(industry='textile', framework='GRI', top_k=40)]
       三方合併：
       - shared_kb/industry-packs/textile.md：22 項
       - GRI 標準議題庫：13 項
       - client entities/topics/ (上年資料)：18 項（有重疊）
       去重後 28 個 candidates：
         環境 8 / 社會 14 / 治理 6
       要列出每個議題的 axis + industry_specificity + source 嗎？
```

`search_topics_universe` 同時讀三個來源：

- **`shared/industry-packs/<industry>.md`**：susr 內建的產業議題包，每年由 susr 維護者更新
- **框架標準議題庫**：GRI / ISSB / ESRS / TW_FSC / SASB 標準揭露項對應
- **客戶 `entities/topics/*`**：你過去評過的議題（跨年連續性）

結果是 deduplication 後的 candidate list，每個 candidate 標 `source_kb` 讓你知道來自哪一邊。

### Step 2：跟客戶議合（議合事件結構化）

開員工問卷的議合：

```
顧問：記一筆 2025 員工問卷議合 — N=254 全員，方法是問卷，
      raised topics 是 S1/S2/S3/S4/S5，findings 是流動率高、夜班疲勞訴求多、
      員工協助方案使用率低。

Claude：[呼叫 stakeholder_engagement_helper]
       已建：entities/stakeholders/員工/engagements/2025-03-employee-survey.md
       自動建 edges：
       - stakeholder_engaged_via (員工 → engagement)
       - engagement_raised_topic ×5 (engagement → S1/S2/S3/S4/S5)
       - topic_identified_by ×5 (S1..S5 → 員工)
       timeline 已留 action_type='ingest'，payload 含 sample_size + findings_summary。
```

這一筆議合事件以後永遠可追溯。半年後客戶問「S3 是誰提的」，timeline 拉得出來。

### Step 3：雙軸評分（每個議題 2-3 分鐘）

逐項評分（或批次提供分數）：

```
顧問：對 E1 (氣候變遷) 評分：
      impact - 嚴重度 5、範圍 4、不可逆性 4、可能性 5
      financial - 規模 4、時間 L、機率 4
      rationale: 旅館業在台灣面臨颱風頻率上升，新店規劃需評估氣候風險。

Claude：[呼叫 score_topic_dual_axis]
       Impact = 4.5, Financial = 4.0 → 列為「核心」
       已更新 entities/topics/E1.md frontmatter。
       timeline 留 verify entry 含原始 7 個分數 + rationale。
```

關鍵：susr **不替你決定分數**。你帶入專業判斷，它負責記錄、normalize、決定 tier、留 audit trail。

### Step 4：跑矩陣 + invariant check（30 秒）

```
顧問：產出 2025 materiality matrix。

Claude：[呼叫 generate_materiality_matrix]
       Matrix: projects/2025-sr/materiality-2025.md
       SVG:    projects/2025-sr/materiality-2025.svg
       I1 violation: E1, E2, S6 為核心議題但 action chain 為空
       I2 通過。
       要先補 IRO 與 action，還是 freeze 矩陣作為 v1？
```

I1 fail 不會擋你 freeze，但會留 violation 在 timeline。你可以決定先 freeze 給客戶看再補 action，也可以先補完再 freeze。

## 省下的時間 / 提升的品質

| 項目 | 過去 | 用 susr |
|---|---|---|
| 議題池蒐集 | 6-7 小時 | 30 秒 + 對焦時間 |
| 議合資料結構化 | 2 小時 | 5 分鐘 / 場 |
| 雙軸評分（28 議題） | 4-6 小時 | 90 分鐘 |
| 矩陣產出 | 1-2 小時 | 30 秒 |
| **議題池階段總時間** | **8-12 小時** | **2-3 小時** |

品質提升：

- **沒有議題會漏**：三方合併 + 上年連續性
- **每個分數可追溯**：timeline 留原始 7 個分數 + 評分理由
- **議合事件結構化**：哪場議合提出哪些議題自動建邊
- **核心議題自動 sanity check**：I1 invariant 在 commit 前提醒你 action 缺口

## 進階提示

**議題評分顧問之間不一致時怎麼辦**

susr 的 actor 欄位區分評分者。你跟資深同事兩人各自評，timeline 會留兩筆 verify entry。你可以後續 comment 解釋為何取某一組分數，這在跨年回顧時非常有用。

**客戶 CSO 想自己參與評分**

把客戶 CSO 也當 actor（例如 `client:cso:wang`）。所有評分留痕，後續確信時可以說明哪些是顧問評、哪些是客戶評、哪些是共識。

**新議題冒出來時**

不在 industry-pack 也不在框架庫的新議題（例如某產業突發危機），直接在 `entities/topics/` 新增一個 markdown 檔，susr 會 ingest 進 brain。如果這個議題後續變成行業共通的，可以 `promote_to_consultant_kb` 上去，下次你接同行業就會被 `search_topics_universe` 帶回來。

## 對應原則

- **Double Materiality**：雙軸獨立評分是 first-class capability
- **Auditable Trust**：每個分數的時間 + 評分者 + 原始分數全留
- **Anti-Greenwashing**：I1 invariant 防止「核心議題沒 action」這種綠漂結構
