# 場景：客戶今年要重述去年範疇 3

## 30 秒先看這段

客戶今年要把去年範疇 3 從 1,200 tCO₂e 改成 1,580 tCO₂e（納入外包員工通勤），這在永續報告書世界叫「重述（restatement）」。過去你要手算變動 %、手翻舊 Excel 找原始值、手寫附註、自己提醒自己不要漏揭——容易出包，確信師翻起舊帳一翻就破。

susr 自動算變動 = 31.7%、超過 5% 閾值就 snapshot 鎖住原始版本、強制你寫重述原因、整條證據鏈在確信師面前一秒拉出來。你只需要決定「重述理由怎麼寫」這件需要人腦的事。

---

## 痛點

重述（restate）是顧問實務最容易翻車的場景之一，因為它同時牽動：

- **客戶問**：「為什麼今年揭露的去年數字跟去年報告書不一樣？」
- **確信師問**：「請提供原始計算過程、邊界變動依據、新舊值差異分析」
- **主管問**：「上下年數字不一致這件事你有揭露嗎？閾值符合 GRI 揭露要求嗎？」
- **客戶內部稽核問**：「你們今年怎麼改的、誰簽核的、什麼時候改的？」

而觸發重述的情境很多，每種都棘手：

- 去年算錯（活動資料誤植 / 排放因子用錯版本 / 換算單位錯）
- 邊界改了（併購新工廠 / 納入原本忽略的外包員工 / 供應鏈範疇擴大）
- 計算方法升級（IPCC AR5 → AR6 / 環境部排放因子改版 / GLEC 物流標準更新）
- 揭露指引變了（GRI 305 改版 / ISSB S2 強制納入某類別）

每一種都意味著「歷史數字必須改」，但又不能「悄悄改」。

---

## 過去怎麼做

典型 workflow（一次 restate 吃掉 4-8 小時）：

1. 翻去年 Excel 找原始計算欄位（30 分鐘 - 1 小時）
2. 翻去年報告書 PDF 確認當時揭露值（15 分鐘）
3. 開新 Excel 跑新邊界 / 新方法重算（1-2 小時）
4. 手動算變動 % = (新值 - 舊值) / 舊值，判斷是否超過揭露閾值（5 分鐘 + 經常算錯）
5. 翻 GRI 2-4 / ISSB 揭露要求複習揭露格式（20 分鐘）
6. 寫「重述揭露表」附註（重述項目 / 原始值 / 重述值 / 變動 % / 重述原因 / 校正方法）（1 小時）
7. 把附註塞進報告書相應章節 + 對照表（30 分鐘）
8. mailbox 找客戶當時寄來的「外包員工名單」當佐證（20 分鐘）

最痛苦的：第 4 步「手動算 %」常常算錯閾值（特別是有負值或 baseline 為零的情境），漏揭露閾值就會被確信師抓。第 6 步「重述揭露表」格式每家顧問公司不一樣，每次都要重做。

## 省下的時間 / 提升的品質

| 項目 | 過去 | 用 susr |
|---|---|---|
| 翻舊 Excel 找原始值 | 30 分鐘 - 1 小時 | 0 秒（page_versions 內） |
| 手動算變動 % | 5 分鐘（常算錯） | 0 秒（brain 算） |
| 判斷是否超過揭露閾值 | 人工查指引 | invariant 自動跑 |
| 寫重述揭露表附註 | 1 小時 | 5 分鐘（補 narrative 即可） |
| 找佐證 source document | 20 分鐘 | 0 秒（source_ref 已綁） |
| 確信攻防回應 | 1-2 小時 | 30 秒 |
| **單一 restate 總時間** | **4-8 小時** | **15-20 分鐘** |

品質提升：

- **5% 閾值機械化執行**：人腦會忘、會看錯、會自我合理化跳過揭露；invariant 不會
- **snapshot 不可逆**：原始版本永遠在 page_versions 留底，「悄悄改回去」做不到
- **timeline append-only**：每次 restate 都留時間戳 + actor + payload，確信師可信
- **跨年揭露一致**：今年揭露的去年值跟去年報告書的差異被系統強制標記
- **重述揭露表自動產生**：格式統一，引用齊全，符合 GRI 2-4 / ISSB S1 要求

## 常見變體

**邊界擴大（併購 / 新工廠）→ 全段重述**

不只一個 datapoint，是整批 KPI 連動。Claude Desktop 內：「lealea 5364 因 2024Q3 併購 ABC 工廠，所有 scope1/2 datapoint 2024 全年重算，actor=consultant:zhang」。brain 會 batch 跑 write_datapoint_value，逐筆判閾值、逐筆 snapshot、逐筆寫 timeline。揭露表自動列所有變動超過 5% 的項目。

**計算方法升級（IPCC AR5 → AR6）→ 全 KPI 連動**

GWP 值改了，所有含非 CO₂ 氣體的 datapoint 都要重算。brain 用 `datapoint_calculated_with` edge 反查全部受影響的 datapoint，跑 batch restate。揭露表會自動分組「因 GWP 改版而重述」與「因其他原因而重述」。

**排放因子修訂（環境部新版）→ 整年度全 KPI restate**

環境部公告新版電力排放係數，brain 內 `shared/emission_factors/twn-electricity-epa-2025-v1.md` 升級後，跑 `recompute_dependents(emission_factor='twn-electricity-epa-2025-v1')`，所有引用該因子的 datapoint 自動重算 + 走 restate 流程。

**未達 5% 也想揭露 → 自願性揭露**

有時 1-3% 的變動雖未達強制閾值，但客戶基於透明度仍想揭露。可以呼叫 `write_entry(action_type='comment', payload={voluntary_disclosure: True, ...})` 主動留痕。揭露表會把它歸到「自願性揭露」段落。

## 一個實戰提示

restate 前先跟客戶對齊兩件事：

1. **這次重述會不會牽動目標達成揭露？** 例如重述後去年範疇 1+2 從「達標」變「未達標」，那 `target` entity 的 `achievement_status` 要連動改，I3 invariant 會檢查 verification_path 是否更新。
2. **重述揭露要不要回溯改舊報告書？** 一般做法是「在新報告書揭露重述，不改舊報告書 PDF」。susr 預設這條路（page_versions 保留舊值即等同於舊報告書版本「可考」），但你需要在揭露表內主動說明這點，免得讀者誤會。

這兩件事 susr 不會替你問客戶，是你的工作。
