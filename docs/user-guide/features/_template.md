# Feature 寫作模板

> 這份是給未來寫 `features/*.md` 時填用的骨架。把這個檔案 copy 一份重命名即可開始。
> 三段式結構，**前 100 字必須在 30 秒內回答「這個功能怎麼幫我」**。

---

## [Feature 名稱]

### 30 秒先看這段

[**100 字以內**，前 30 秒讓顧問知道：這個功能解什麼痛點、用一次節省多少時間、最關鍵的設計取捨。
不要寫「我們的 X 提供 Y 能力」這種句法。寫「過去你要 A，現在你只要 B」。]

範例：
> 過去要決定議題池你要翻 GRI / 同業 / 監管要求湊 30+ 議題，平均吃 6 小時。
> `search_topics_universe` 從產業包 + 框架庫 + 客戶上年議題三方合併，30 秒給你
> 去重後的候選 list，每個議題標 source。剩下的時間留給跟客戶 CSO 對焦。

---

### 什麼時候用 / 解什麼痛點

[列出 2-4 個顧問日常場景，每個場景描述：
- 什麼觸發顧問需要這個功能
- 不用這個功能時顧問怎麼做（痛點具體化）
- 用了之後 workflow 變成什麼樣

跟 `scenarios/` 對應的場景請加 link。]

範例：

**場景 1：接到新客戶第一週**
- 觸發：客戶簽約，你要在 kickoff 前準備議題池草案
- 過去：翻 GRI Sector Standard PDF 抄通用議題（2h）+ 找同業報告書（3-4h）
- 現在：一句話拉出 28 個候選，把時間留給跟客戶 CSO 對焦

對應場景文件：[`scenarios/接到新客戶第一週.md`](../scenarios/接到新客戶第一週.md)

---

### 為什麼這樣設計

[連結到 `philosophy/` 解釋設計取捨：
- 為什麼這個 feature 是 Co-pilot 而非 Replacement
- 跟哪一條哲學最相關
- 有什麼**刻意不做**的（防止顧問誤解功能邊界）

避免重複 `philosophy/` 內容，用 1-2 句引用 + link。]

範例：

這個 feature 不替你決定議題重大度，只把候選 list 湊齊——對應
[`philosophy/co-pilot-not-replacement.md`](../philosophy/co-pilot-not-replacement.md)
的「susr 把記憶外部化，判斷仍是你」原則。

**刻意不做**：susr 不會根據 LLM 主觀判斷自動把某議題標為「重大」。所有評分必須走
`score_topic_dual_axis` 並由 actor=consultant 簽核。這是反綠漂的結構性防線。

---

### 寫作 checklist（給作者自查）

寫完 feature 文件前自問：

- [ ] 前 100 字讀完，顧問能說出「這幫我什麼」嗎？
- [ ] 場景是顧問真實會遇到的，還是工程師想像的？
- [ ] 有沒有寫成 API doc？（如果有，重寫）
- [ ] 有沒有用「我們的 X 提供 Y...」這種句法？（如果有，改成「過去你要 A，現在 B」）
- [ ] 連結到 philosophy / scenarios 了嗎？
- [ ] 有沒有寫「刻意不做」？（防止顧問誤解邊界）
- [ ] 繁體中文、平鋪直敘、少用括弧
